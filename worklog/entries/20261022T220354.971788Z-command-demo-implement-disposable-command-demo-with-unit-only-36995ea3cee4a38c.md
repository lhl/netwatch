# Implement disposable command demo with unit-only verification

## Summary

Implement the self-contained `autoprotect.demo.run_demo() -> dict` command demo and deterministic tests without executing the concurrently developed CLI. The owned implementation and unit/syntax checks are complete. Actual CLI, module entry point, installed-package execution and independent review remain parent integration dependencies; this entry does not claim that the real command demo has passed.

The demo uses invented public data and private temporary state only. It neither loads caller policy nor collects host inventory, fetches feeds, invokes native package tools, grants provenance, or changes runtime authorization rules.

## Changes

- Added only `autoprotect/demo.py`, `tests/test_demo.py`, and this unique handoff entry. Shared runtime, CLI, documentation, packaging and examples were not edited. No staging, commits, branches, worktrees, agents or schedules were created.
- `run_demo()` accepts no arguments. It generates strict manual/automatic simulator policies, two invented Debian package/advisory pairs, a synthetic repository catalog, a segregated example incident, and private JSON files under its own `TemporaryDirectory`. Fixture files are created exclusively with mode 0600; scenario subdirectories use mode 0700. Runtime code does not import repository tests or fixture files.
- Every lifecycle operation uses a separate ordinary `[sys.executable, '-m', 'autoprotect', '--state-dir', DIR, '--policy', FILE, COMMAND...]` invocation through the reviewed `Runner`. The demo never permits `poll`, `--live`, or native tools. Runner supplies `shell=False`, a minimal environment, process-group termination and graceful interruption cleanup. Working directory is the package parent, not the caller directory; source and installed execution need no inherited `PYTHONPATH`.
- Commands have a 15-second execution deadline, a shared 120-second command-session budget, a 128-command ceiling and a 256 KiB combined stdout/stderr cap. Strict JSON decoding additionally bounds depth and node count. Successful results, failed execution outcomes and denied actions must appear on their contract-defined streams with the expected exit status. Nonzero exit alone never establishes a successful negative test. Public errors use one bounded application message without child logs or OS paths.
- Four separate scenarios cover manual approval and success, denial before approval, repeat-execution denial, automatic success with no approval command or approval audit event, before-write confirmed failure with unchanged full inventory and cleared gate, and after-write uncertainty with changed state and a retained gate. Both feeds are imported twice and their snapshot identities/provenance checked. Queue, audit, full inventory fingerprints, triage/export and recovery-status corroborate result claims.
- The after-write scenario creates and approves a second package plan against the already changed inventory. Its execution is blocked while the first gate remains. Explicit resolution must retain `verified=false` and the original `needs_attention` status while clearing the exact gate and changing the generation. Planning before recollection is denied. Fresh collection does not revive the old approved plan: execution must deny it as stale, with a generation-related audit reason. A new generation-bound plan and approval then succeed after the temporary simulator failure control is cleared.
- Direct backend calls are limited to actual `Simulator.set_failure` controls on this invocation's generated state. Neither gate files nor database authority are fabricated by runtime demo code. A result is returned only after temporary-state removal. Its JSON is capped at 8 KiB and discloses synthetic evidence, non-authenticated actor labels, package-state versus runtime-health limits, attestation versus rollback, and forced-death cleanup limits.
- Tests were written alongside the new module. Fixture and process-helper unit tests use fake child results; orchestration tests replace only the demo runner with a test dispatcher that opens fresh actual Store/Engine/Simulator APIs per command. That dispatcher uses ordinary imported provenance and generated policy, with no clock, fetcher or native-trust injection. It does not validate actual CLI parsing, dispatch, protected-file loading or packaging.
- Added separately named `DemoCLIIntegrationTests.test_real_cli_disposable_demo`. It deliberately requires real child CLI processes and does not skip a missing/broken CLI. It was excluded from this child's `-k Unit` selection and must be run by the parent after the stable CLI handoff.
