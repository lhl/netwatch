# Implement persistent policy approval and execution lifecycle

## Summary

Implement the task-7 persistent Store/Engine lifecycle without editing the independent backend, CLI, shared contracts, or parent integration tests. Authorized manual and automatic synthetic executions now reach independently verified success; observe mode, stale or changed inputs, spoofed provenance, and unsupported findings cannot grant mutation. Uncertain execution retains a backend recovery gate. This completes the assigned implementation and focused-test unit, not the parent integration/review milestone.

## Changes

- Created `autoprotect/store.py`, `autoprotect/engine.py`, `tests/test_store.py`, and `tests/test_engine.py`. No dependency, metadata, existing runtime, CLI, shared-document, or other worker file was changed. No files were staged or committed.
- Store schema version 1 uses content-addressed `objects` for source, inventory, finding-set, plan, and approval bodies; `source_health`, `inventory_heads`, `finding_index`, `plan_status`, and `approval_heads` are separate mutable indexes. `outcomes` and `audit` are append-only records. Immutable-object and outcome reads verify their hashes; update/delete triggers reject ordinary changes to objects, outcomes, and audit. Hashes and local triggers are not protection against a database writer.
- SQLite enables foreign keys, a 5,000 ms busy timeout, and synchronous FULL. Schema initialization is idempotent, rejects version mismatches/unknown existing schemas without deleting data, and uses explicit transactions. Writes require `Store.transaction()` with `BEGIN IMMEDIATE`; conditional claim and execution-start audit commit together. `close()` and context-manager use are implemented.
- Policy validation rejects missing/extra fields, invalid types, duplicate or unsafe identities, invalid origin tuples, and excessive durations. The chosen duration bound is 1 through 31,536,000 seconds, matching existing matcher validation. Asset/package lists contain 1 through 10,000 identities; origin lists contain at most 256 exact tuples. Native policy requires nonempty approved origins and a configuration digest; its execution permission also requires the three explicit script/recovery/lineage assertions. Policy lists are canonicalized before hashing.
- `Engine(store, policy_provider, backend, *, clock=core.now, fetcher=None)` preserves the assigned methods and JSON return envelopes. `fetcher` is a constructor-only testing dependency; the default remains the fixed-endpoint adapter. The policy provider must be callable and is reloaded at authorization boundaries, after preparation, after claim commit, and immediately before installation. Labels identify an audit assertion, not an authenticated user.
- Import rejects non-import acquisition arguments, supplied HTTP validators, and acquisition/provenance body envelopes. Ordinary unknown feed fields confer no trust. Only successful `poll` creates HTTPS-acquired snapshots; import and HTTPS snapshots have different content identities and cannot rewrite each other's provenance. Poll holds the write transaction through acquisition so concurrent responses/imports cannot replace a newer head out of order. A 304 needs a previous same-source HTTPS snapshot and a stored valid request ETag. Poll returns the source-health summary on fetch/parse failure, retaining the last good head/success time and recording a bounded error; KeyboardInterrupt records failure then propagates. A savepoint also rolls back a tentative successful head if acquisition audit persistence fails.
- Source bodies bind normalized records, their digest, parser version, source ID, acquisition mode, and fixed endpoint. Identical normalized content/provenance deduplicates. Current source errors/staleness produce visible unknown findings, not empty successful coverage. Export is an explicitly untrusted data envelope containing inventory, source health, findings, relevant Debian assertions, and incident text; executable-looking text stays data.
- Plans bind the full repository target, immutable finding/source/inventory identities, full inventory fingerprint excluding only observation time, policy digest, and expiry. Fresh identical observations can replace an inventory head without invalidating its fingerprint; any other inventory change invalidates the plan. Manual approval binds plan/policy/actor/creation/expiry, with expiry capped by the plan. Source corrections, artifact changes, expired approvals, invalid policy, and corrupted immutable bodies are checked before mutation. Final plans cannot rerun.
- Execution holds the backend target/native lock from preflight through gate creation, claim, mutation, independent observation, outcome persistence, and gate finish. The backend gate is created before the executing transaction commits. After claim commit, a new write transaction reloads and revalidates all authorization and stays open through download, callback, installation, full-inventory-delta verification, and outcome commit. This prevents source/inventory/approval changes in another Store from crossing the final authorization boundary. The callback repeats inventory, artifact, freshness, plan, approval, and policy checks after download. The backend's returned status is never a success certificate or an unrestricted audit payload.
- Successful verification requires the complete normalized post-state to equal the pre-state with only the approved binary/source version replacements. Added/deleted/unrelated/held/non-ready package changes and unavailable/future observations retain the gate as `needs_attention`. A confirmed pre-mutation BackendError commits `failed` before clearing its gate. Indeterminate errors, interruption, unexpected apply failures, persistence uncertainty, and repeated mutation callbacks retain the gate. A gate-clear failure after committed outcome is reported as indeterminate rather than falsely described as pre-mutation failure.
- `recover` takes recovery locks and changes abandoned executing work to `needs_attention` without mutation or success promotion. `resolve_recovery` records actor/reason before clearing an exact prior gate under recovery locks, and records completion afterward. It also handles a gate written before the claim committed and a gate retained after a successful outcome committed. It never makes unresolved work successful. There is no lease or automatic rollback.
