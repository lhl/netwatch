# Bound triage output, verification cost and evidence retention

## Summary

A critical review against the real Debian tracker feed (86 MB, 77,414 trixie records; `linux` alone has 20,410) found three problems in the delivered proof of concept. First, whole-host triage failed outright ("exceeds the output byte limit") for a host with five binaries from the `linux` source, because findings were emitted per binary per assertion. That also blocked planning for every package. Second, a simulator lifecycle took 83 s per `execute` and 20 s per `plan`: each re-validation reloaded and re-hashed the 52 MB snapshot and re-matched the whole host while holding the SQLite write lock. Third, immutable findings sets (14-58 MB per triage) and every polled snapshot accumulated without any way to prune them.

Outcome: findings group one package's assertions by remediation identity. All not-affected assertions share one row; affected assertions get one row per Debian fixed version (one upgrade decision); evidence-level unknowns are grouped by explanation; an unassessable package gets one unknown row. Each row lists every covered advisory in `advisory_ids`, which replaces the single `advisory_id` in findings and plans. Planning and execution re-derive that exact advisory group for the bound package only. Unreferenced evidence is pruned transactionally, polling no longer holds the write lock during acquisition, and inspection commands read without it. Findings record `evidence_acquisition` (https/import). Plans and findings from the previous format are treated as stale, not crashes.

## Changes

- `autoprotect/matching.py`: `_groups()` groups verdicts; `match()` emits grouped rows with `advisory_ids` and `evidence_acquisition`, computing verdicts once per source identity. New `verify_affected()` recomputes one exact affected group from a single source package's assertions.
- `autoprotect/engine.py`: `_finding_context` uses `verify_affected`. Plans bind `advisory_ids`. Legacy plans and findings without `advisory_ids` become stale. Triage persists only affected findings and records acquisition. `poll` fetches and parses outside any transaction, installs only if the head revision is unchanged (otherwise it discards the response, records `source-error` and raises), and keeps the savepoint that preserves a failed-acquisition record. Import, poll and triage call `_prune()` and audit `evidence-pruned`. `queue`, `audit` and `recovery-status` use `Store.read()`. The source content digest is checked once per verified snapshot ID.
- `autoprotect/store.py`: schema version 3 adds `finding_sets(set_id, inventory_id, source_digest)`, and the object delete trigger now permits only `source`, `findings` and `inventory` kinds. Version-2 stores migrate in place without data loss. New `read()` (deferred) and `prune()`. `get()` re-parses byte-identical previously verified canonical text (at least 64 KiB, 4-entry LRU) without re-validation; any changed bytes are fully re-verified.
- Tests: `tests/test_matching.py`, `tests/test_engine.py`, `tests/test_store.py` add grouping, outdated-host scale, exact-group verification, provenance, retention, concurrent-poll, non-blocking read, migration and cache-tamper cases. Pipeline/CLI tests now search `advisory_ids`; the final-callback timing tests hook `verify_affected` (the replacement costly pass).
- Docs: `docs/DESIGN.md` (finding and plan schemas, grouping, retention, schema 3 and migration, polling and read concurrency), `docs/OPERATIONS.md` (reading grouped findings, retention, concurrency) and `examples/README.md`.

## Validation

- `python3 -m unittest discover -s tests`: 465 tests OK.
- `git diff --check`: clean.
- Real-feed measurements (scratch scripts, feed downloaded once from the fixed tracker endpoint, synthetic inventories, nothing installed). Worst case (every package at `1.0-1`): 5 `linux` binaries went from failure to 1,760 rows (2 MB, 1.1 s); a desktop-shaped inventory went from 73,004 rows (57 MB) to 2,060 rows (2 MB).
- Simulator lifecycle with the real feed and about 1,500 packages: plan 20 s to 0.6 s, execute 83 s to 2.1 s; database after one cycle 95 MB to 54 MB (the one retained snapshot).
- Not tested: a real native host, or concurrent CLI processes against one database beyond the two-connection test.
