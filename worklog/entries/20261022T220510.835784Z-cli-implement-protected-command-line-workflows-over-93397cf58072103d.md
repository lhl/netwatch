# Implement protected command-line workflows over reviewed runtime

## Summary

Implement the assigned command-line boundary over the reviewed runtime at `499d974`, without changing runtime authorization, backend behavior, package metadata, shared documentation, or another worker's files. The CLI and multiprocessing-safe module entry point are implemented. All 41 focused offline CLI tests pass, including an ordinary multi-process manual simulator workflow. This is a child implementation handoff; packaging, actual demo integration, integrated checks and independent review remain the parent's responsibility.

## Changes

- Added only `autoprotect/cli.py`, `autoprotect/__main__.py`, `tests/test_cli.py` and this entry. No staging, commits, branches, worktrees, agents or schedules were used.
- `main(argv=None) -> int` is the console entry-point interface. Operational commands require explicit `--state-dir DIR --policy FILE` before the command. The validated policy alone selects the backend. There are no backend, repository endpoint, runner, clock, fetcher, trust or failure-control command-line overrides. Option abbreviation is disabled.
- Implemented `init-simulator --inventory FILE --catalog FILE`, `import-feed SOURCE FILE`, `poll SOURCE`, `inventory [--import FILE]`, `triage ASSET_ID`, `plan FINDING_ID`, `approve PLAN_ID --actor LABEL`, `execute PLAN_ID`, `queue`, `audit`, `export ASSET_ID`, `recovery-status PLAN_ID`, `recover PLAN_ID`, and `resolve-recovery PLAN_ID --actor LABEL --reason TEXT [--malformed-digest SHA256]`. Source IDs are exactly `pwn` and `debian`. Dispatch calls Engine APIs rather than duplicating authorization or issuing SQL.
- `demo` rejects operational global options and lazily imports `autoprotect.demo.run_demo()` only when selected. Its test substitutes an in-memory mock module. The unstable demo worker module was not inspected, edited or run. Help/version do not load policy or open state. `__main__.py` calls `main()` only under `if __name__ == "__main__"`; a multiprocessing-import test verifies no dispatch.
- Policy uses a callable provider that re-reads `local_files.read_bytes(private=True, live=...)`, parses and validates on every Engine request, and rejects a backend change after initial selection. The cap is 1 MiB. Imports use bounded regular-file reads: 8 MiB for pwn, 128 MiB for Debian, and 64 MiB each for inventory/catalog. A JSON null inventory is explicitly rejected, so it cannot become Engine's `None` request for native collection.
- State uses `local_files.prepare_database` and its fixed `state.sqlite3` path. Simulator state is fixed at `DIR/simulator.json`. Backend construction is deferred until a backend method is actually needed; feed, queue, audit, imported-inventory, triage and export paths do not accidentally observe native inventory. Imports retain `acquisition=import` and force `collector=imported`, removing collection authority regardless of input labels.
- Native `execute`, `recovery-status`, `recover` and `resolve-recovery` require `--live` and effective root before database preparation or backend construction. Every live request uses protected live policy/state checks. Simulation rejects `--live`. Explicit native collection without `--live` passes `live=False`; tests substitute a fake native backend, not a native test mode exposed by the CLI.
- `init-simulator` accepts only a simulator policy, rejects pre-existing fixed database/simulator/coordination state, and uses `Simulator.initialize` for exclusive publication. Input/policy paths cannot collide with database files, sidecars, simulator state, locks, gates, generation files or the two fixed simulator publication aliases. Those aliases matter because backend recovery can remove an unpublished gate preparation file. Noncolliding input files inside the private state directory remain usable. Setup returns `{status: initialized, backend: simulator, simulation_only: true, state_dir, simulator_path, inventory: {id, body}}`; the inventory is actual simulator collection saved through Engine, not an imported native claim.
- Successful output is ASCII-escaped JSON on stdout. Application/argument errors are one JSON object on stderr: `{error: {code, message}}`; messages are capped at 2,048 characters. Unexpected OS, SQLite and other exceptions receive fixed diagnostics, not their raw messages or tracebacks. Help/version are plain text. Exit codes are 0 for successful commands, 1 for application errors or failed poll/execution outcomes, 2 for arguments, and 130 for interruption with queue/recovery guidance. Failed poll/execution summaries remain structured stdout results. Successful explicit recovery can return `needs_attention` with exit 0 and `verified=false` (nested in `result` for `recover`). Export preserves the runtime's `trusted=false` untrusted-data envelope.
