# Repair command startup ownership and interruption cleanup

## Summary

Repair the task-5 review findings without changing the runner/frontend-lock public APIs or implementing backend/lifecycle behavior. A synthetic KeyboardInterrupt could previously leave a command alive when Popen returned before Runner entered its cleanup try block, or while Popen itself was still initializing. A post-exec handshake OSError was also incorrectly reported as a definite pre-mutation BackendError. The repair owns the process before initialization, keeps cleanup active across startup, and treats unconfirmed startup as indeterminate.

This entry corrects the unconditional spawn-failure and interruption-cleanup claims in `worklog/entries/20261022T201539.964198Z-inventory-runner-implement-normalized-inventory-and-bounded-comma-9d2a5aa0fa27cb5a.md`. It does not modify that entry. All processes and locks exercised here are synthetic; no host inventory, package operation, backend, lifecycle, staging, or commit was performed. The initial provider transport failure did not apply an edit; both assigned files were reread before continuing, and no repeated provider failure occurred.

## Changes

- `autoprotect/runner.py`: a private Popen subclass is allocated without starting a process, then initialized inside the cleanup scope. Its PID and stream handles remain reachable if Popen initialization fails after creating the child. This closes both the Runner line gap and the Popen-constructor return gap, not just the originally reproduced line.
- Temporarily defer callable SIGINT handlers in the main thread across spawn and cleanup, preserving the child's signal mask. Deliver pending interruption only at checks inside the cleanup-protected body. Output and exit waits check at intervals of at most 0.1 seconds; handler restoration occurs after cleanup. This also avoids a second Ctrl-C bypassing cleanup during the transition into finally. Non-main-thread execution remains supported; Python dispatches signal handlers in the main thread.
- Cleanup kills the command process group, closes its pipes, and waits up to one second for its leader. If interrupted startup precedes creation of the child's new session, a missing group falls back to killing the leader and then retries the group lookup to catch a concurrent setsid/descendant creation. Cleanup completes before unwinding the enclosing frontend-lock context in the tested graceful failure paths.
- `Runner.run(argv, *, timeout=60, cwd=None)`, `Runner.dpkg_frontend_lock()`, `Runner(max_output_bytes=...)`, and `CommandResult` are unchanged. Successful and nonzero exit results, validation, minimal environment, output limits, and pre-spawn lock checks retain their semantics. KeyboardInterrupt still propagates after cleanup; it never proves that mutation did not begin.
- Startup OSError, ValueError, and subprocess handshake errors now raise bounded `IndeterminateError`, including missing-executable/cwd failures. This conservative broadening is intentional: Popen's public exception type does not establish that execution never started, and inspecting an error message or errno cannot establish that guarantee. Validation and environment/lock checks still run before any spawn attempt and keep their existing error types.
- `tests/test_runner.py`: red-first trace injections at Runner handle registration, Popen constructor return and internal PID registration; real SIGINT between native spawn return and PID assignment; post-exec handshake OSError; repeated SIGINT during cleanup; prompt SIGINT handling during output/exit waits; unchanged signal handler/mask; and non-main-thread startup. A synthetic first-group-lookup failure with a real descendant also reproduces the setsid race. Tests observe socket EOF, reaped leader and closed pipes before the temporary frontend-lock descriptor closes, and provide explicit fallback cleanup even when a regression fails.
- Updated runner docstrings with the startup classification, interruption behavior and containment limits. No shared design, delivery or review files were edited.
